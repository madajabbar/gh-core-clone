THE WIRE CONTRACT (implement every line):

REST v3 under /api/v3 (all JSON, must send X-GitHub-Request-Id):
- GET /api/v3/ → 200 JSON, header X-OAuth-Scopes: 'repo, read:org'
- GET /api/v3/meta → 200 {"installed_version":"..."} (non-empty)
- GET /api/v3/user/repos → 200 array of repo objects
- POST /api/v3/user/repos → 201, the repository object {name, full_name, owner:{login}, ...}
- GET /api/v3/repos/{owner}/{repo} → 200 repo; 404 JSON if missing (a repo under a different owner is 404, never 403)
- PATCH /api/v3/repos/{owner}/{repo} → 200, description updated
- DELETE /api/v3/repos/{owner}/{repo} → 204; later GET → 404
- PUT /api/v3/repos/{owner}/{repo}/contents/{path} → 201 on create, 200 on update, 409 on stale sha
- DELETE /api/v3/repos/{owner}/{repo}/contents/{path} → 200 {commit:{sha}}; later GET → 404
- POST /api/v3/repos/{owner}/{repo}/labels → 201 {name}; a label must exist before an issue may carry it
- POST /api/v3/repos/{owner}/{repo}/issues → 201, open issue; 422 if it names a nonexistent label
- POST /api/v3/repos/{owner}/{repo}/pulls → 201, state open, with head and base fields
- GET /api/v3/repos/{owner}/{repo}/pulls/{number} → 200; 404 if unknown
- PUT /api/v3/repos/{owner}/{repo}/pulls/{number}/merge → 200 {sha, merged:true, message}; 404 unknown pull, 405 conflicted

Git smart HTTP at /{owner}/{repo}.git:
- Repos are created via REST POST /api/v3/user/repos. A push cannot invent one.
- The suite speaks smart HTTP in-process (no git binary). It expects:
  - GET /{owner}/{repo}.git/info/refs?service=git-upload-pack → protocol v2 advertisement opening with "version 2" (the suite sends Git-Protocol: version=2). Must support v2 capability advertisement and ls-refs. If you can only do v0, it loses 3 checks but works otherwise.
  - POST /{owner}/{repo}.git/git-upload-pack → the v2 ls-refs / fetch response (packfile or negotiation).
  - GET /{owner}/{repo}.git/info/refs?service=git-receive-pack → v0 advertisement opening with "# service=git-receive-pack", advertising report-status, side-band-64k, delete-refs.
  - POST /{owner}/{repo}.git/git-receive-pack → apply the push. Must support report-status, side-band-64k. Every update must fast-forward: non-fast-forward → "ng <ref> non-fast-forward" per ref, and the ref does not move.
  - Missing repo → 404 on both services' /info/refs.
- This is the single hardest part. You MUST implement a working smart-HTTP pack protocol: parse the pkt-line framing (4 hex length prefix), the ref advertisement, ls-refs, and receive-pack's commands. For push you need to at least store the new ref deltas (you can be lenient on actual packfile objects — the suite checks refs move and fast-forward rules, and that clone gets refs/objects back). If implementing full packfile delta decoding is too much, the minimal viable path: maintain refs + a lightweight object store keyed by sha, serve ls-refs and refs, and on receive-pack update refs per the command list (fast-forward checking by comparing parent shas you track).

GraphQL v4 at POST /api/graphql:
- Body {"query":..., "variables":{}} with bearer token; unauthenticated → exactly 401.
- Must handle the documents gh and github-mcp-server send, and introspection:
  - __type(name:"Issue") lists id, number, title, state, body
  - __type(name:"PullRequest") lists id, number, headRefName, baseRefName, mergeable, state, merged, files
  - __type(name:"Repository") lists id, databaseId, name, nameWithOwner, owner, defaultBranchRef, viewerPermission, hasIssuesEnabled, issue, issues, pullRequests, pullRequest
  - SearchType enumValues include ISSUE
  - repository.issues with orderBy:{field:CREATED_AT,direction:DESC} returns numbers descending, ties by number DESC; states:[OPEN] omits closed
  - createPullRequest takes repository id + head branch (pushed over git), opens a PR REST reads back with same head/base
  - Two operation documents in one body → two results in order
  - Query naming unknown field → HTTP 200 with errors array naming it
  - Unknown repository → data.repository = null with no errors
- Implementation: implement a minimal GraphQL query executor over your store. Introspection is essential (__type, fields, enums). A simple resolver that walks the query AST against your in-memory model and answers the known shapes is enough — you don't need a full GraphQL library, but you can't depend on one (no install). Write a small executor.

MCP at POST /mcp:
- JSON-RPC 2.0 over Streamable HTTP, answering application/json or text/event-stream. Each request answers inside 3 seconds.
- Revision 2026-07-28: every request declares it, server/discover answers a result whose supportedVersions is a non-empty list of YYYY-MM-DD revisions. Also support handshake 2025-11-25 via initialize + notifications/initialized with optional Mcp-Session-Id.
- tools/list offers at least 6 tools: create_repo, get_repo, create_issue, list_issues, create_pull_request, merge_pull_request (a server prefix allowed, matched case-insensitively as suffix). Every tool needs a non-empty description and inputSchema {type:"object"}. Two tools/list calls answer byte-identical lists.
- tools/call with the args github-mcp-server documents: create_repo {name}, get_repo {owner,repo}, create_issue {owner,repo,title,body?}, list_issues {owner,repo,state?}, create_pull_request {owner,repo,title,head,base}, merge_pull_request {owner,repo,pull_number}. Map each arg onto your schema's nearest property. Fill a full_name property with owner/repo.
- Two in-flight requests keep their own JSON-RPC ids and answer for their own args.
- Unknown tool → -32602 or -32601, never HTTP 500. Missing required arg → isError:true or -32602. Non-JSON body → HTTP 400 with -32700. No Authorization header → 401.
- MCP tools act on the SAME store as REST: a repo/issue created over MCP reads back over REST as the same object.
